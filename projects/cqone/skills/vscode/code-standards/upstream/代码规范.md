# 格式化规范

参见：代码规范-idea设置.md

# 命名规范

## 原则

- 所有地方对同一个事物的命名应该尽量统一
    - 例如：假设副本模块把副本命名为dungeon，那么其他模块就不要把副本相关的类或变量命名为copy、fuben等
    - 例如：假设异兽模块把异兽命名为rahi，那么其他模块就不要把异兽相关的类或变量命名为pet、animal、yishou等
- 在含义清楚的的前提下，应该尽量用短一点的词；但不要一味求短，如果短到引起了歧义，就不好。
    - 能用一个词表达的，就不要用两个词
    - 有约定的简写的，就用约定的简写，不要自己发明简写，约定的简写比如：
        - 循环中，i 是 index 的简写，表示索引
        - cur 是 current 的简写，表示当前
        - prev 是 previous 的简写，表示前一个，对应的 next 表示后一个
        - w 和 h 分别是 width 和 height 的简写，表示宽 和 高
        - img 是 image 的简写，表示图片
        - btn 是 button 的简写，表示按钮
        - txt 是 text 的简写，表示文本
        - win 是 window 的简写，表示窗口视图
        - len 是 length 的简写，表示长度
        - num 是 number 的简写，表示数字或数量
        - arr 是 array 的简写，表示数组
        - str 是 string 的简写，表示字符串
        - fn 是 function 的简写，表示方法
        - src 和 dst 分别是 source 和 destination 的简写，表示一项操作的源和目标
- 避免与语言和引擎的关键字重名
- 全大写缩写的单词，当出现在驼峰名字中时，要转成首字母大写后面的字母小写。比如：RMB、GBK、UTF，分别要用：Rmb、Gbk，Utf

## 模块文件夹名

- 格式：小写字母开头的驼峰
- 要求：含义清楚的前提下尽量简短，尽量使用单个词，尽量不与js自带关键字、工具类同名。要经过主程许可。
- 示例：bag, player, myPlayer

## 类名

- 格式：大写字母开头的驼峰
- 要求：含义清楚的前提下尽量简短。
- 前缀：除core、base、common等底层或公共模块外，ctrl和data文件夹下的类要以模块名开头，view文件夹下的类也尽量以模块名开头。
- 后缀
    - 模块控制器：Ctrl，xxx模块的控制器就叫XxxCtrl
    - 模块数据：Data，xxx模块的数据就叫XxxData
    - 模块事件：Event，xxx模块的事件就叫XxxEvent
    - 模块常量：Const，xxx模块的常量就叫XxxConst。注意放在这个类里的常量是那些零散的常量，如果是枚举型的常量则单独定义一个枚举类，不放这里，枚举类名不要Const后缀。
    - 模块中用于封装配表数据的类（简称：配置对象）：Co，如：道具配置对象ItemCo，装备属性配置对象EquipAttrCo。这些类不需要手写，由工具生成。
    - 模块中用于封装协议数据的类（简称：协议对象）：Po，如：装备页信息协议对象EquipPageVoPo，装备页槽位信息对象EquipSlotVoPo。这些类不需要手写，由工具生成。
    - 模块中用于封装功能数据（通常用于封装配置数据）的类（简称：功能对象）：Fo，如：装备页功能对象EquipPageFo，装备页组功能对象EquipPageGroupFo，装备槽位功能对象EquipSlotFo，装备套装功能对象EquipSuitFo
    - 模块中用于封装服务端信息的类（简称：信息对象）：Mo，如：装备页信息EquipPageMo，装备槽位信息EquipSlotMo
    - 模块用到的各种枚举类：不需要固定后缀，如：装备系统id枚举EquipSysId，装备强化系统id枚举EquipEnhanceSysId
    - 模块中的视图：没有固定后缀，根据视图类型来定，功能界面Win，弹窗Pop，格子Cell，列表项Li，按钮Btn，一般可复用组件Com，一般视图View

## 变量名

- 常量
    - 格式：全大写字母，下划线分词
    - 要求：含义清楚的前提下尽量简短。
    - 示例：CITY_SCENE_ID, MONSTER_TEAM_ID, ID
- 可变量（包括：类成员变量、方法形参、局部变量等）
    - 格式：小写字母开头的驼峰
    - 分类
        - 类成员变量
            - 要求：含义清楚的前提下尽量简短。
            - 示例：bagData, sceneId, scene
            - 特例：视图类中的子视图名
                - 一般视图：v开头，后接用途
                - 按钮：v开头，后接这个按钮点击后要执行的动作，如：穿戴按钮vWear
        - 方法形参、局部变量
            - 要求：含义清楚的前提下尽量简短，另外，由于其作用域不会超出一个方法，相对较窄，在没有歧义的情况下，可以取更简短的名字（相对于类成员变量而言）。
            - 示例：i, index, id, num, len

## 方法名

- 格式：小写字母开头的驼峰
- 要求：含义清楚的前提下尽量简短。一般是动词开头，某些情况下也会用介词开头（如：onXxx, afterXxx, beforeXxx, whenXxx）
- 分类
    - 获取某种布尔状态的方法
        - 要求：使用特定动词：is表达是否, has表达有没有, need表达是否需要, can表达是否能，allow表达是否允许
        - 示例：isMoving是否正在移动, hasSpace是否还有空间, needSpace是否需要空间, canMove是否能移动，allowMove是否允许移动
    - 某事件发生时执行的方法
        - 示例：onAddedToStage视图被添加到舞台上时执行的方法
    - Data类中，处理收到的服务端协议消息的方法
        - 要求：on开头，后接协议类名，去除Po后缀
        - 示例：onSCSynPosition
    - Data类中，发协议消息给服务端的方法
        - 要求：req开头，后面不一定要接协议类名，可以是含义更清楚的名字，以后有时候后端命名的协议名含义不太清楚
        - 示例：reqEnterScene, reqUseSkill
    - 视图里面监听某个数据变更事件，当数据变更事件发生时，刷新数据到视图中的方法
        - 要求：refresh开头，后接需要刷新的数据，
        - 示例：refreshLevel刷新等级到视图中，refreshData刷新全部数据到视图中，refreshHp刷新血量到视图中
    - 其他一般方法
        - 要求：一般以动词开头
        - 示例：init, show, clear, showMsg, addItem, removeItem

# 注释规范

## 类注释

```ts
/**
 * 类说明
 * @author 中文名拼音全拼
 * @since yyyy-MM-dd
 */
```

## 方法注释

- **本类方法**（含 private、getter）均加精简方法注释；优先单行 `/** 说明 */`。
- **父类覆盖方法不加**注释（如 `init`/`onLogout`、`initUi`/`onAddedToStage`/`initData`/`onClose` 等）。
- `@param` / `@return` 默认不用；仅规则复杂时再写；简单参数写进说明句即可（如「cfgId=0 为一键领取」）。

```ts
/** 请求抽奖；drawCb 为恭喜获得内再抽时关闭弹窗 */
reqDraw(idx: number, drawCb?: Callback): void { ... }

/**
 * 方法说明（仅规则复杂时用多行 + 标签）
 * @param id 参数说明
 * @return 返回值说明
 */
```

## 成员变量注释

倾向于单行注释

```ts
/** 变量说明 */
```

- **`v*` FGUI 元素**（与 xml 同名子节点绑定的视图成员）：**默认不写注释**；仅开发者人手主动补充时保留，工具/Agent 不要自动补。

## 方法内部语句块注释

- 不要写没用的注释。
- 如果有需要特别解释的地方，容易引起误解的地方，则需要加注释说明，形式如下。

```ts
// 原因说明
```

# 代码书写顺序与分区规范

## 类成员

按以下顺序：

1. 静态成员变量
2. 初始化性质、get性质的静态成员方法
3. 成员分区行（非必须，视乎有没有静态成员）
4. 非静态成员变量
5. 成员分区行（非必须，视乎非静态变量多少）
6. 构造方法
7. 普通成员方法（包括：所有非静态方法，以及功能型的静态方法）

当类中有较多成员的时候，可以将相关的成员放到一起，分区写，不同区之间用以下分隔行隔开：

```ts
//* ************************************************************************
```

当分区也需要说明的时候，可以如下添加分区说明：

```ts
//* ************************************************************************
//* 分区说明
//* ************************************************************************
```

## 新建模块 Data / View 方法分区

**仅约束新建 / 脚手架生成**；改旧文件勿为排版整文件挪方法（除非明确要求重排）。默认区与区之间空行；方法多或跨职责再加上方分区行。

### Data（`XxxData`）

1. 静态单例 `I`
2. **字段**（全部加注释；private 缓存 → public 状态）— **不放** getter
3. **父类/生命周期**：`init` → `onLogout`（…）
4. **协议收包**：`onSC…`
5. **协议发包**：`req…`
6. **自定义对外接口**：`get*` / `is*` / getter / `open*` / `set*` / `cancel*` 等
7. **私有实现**：`do*` / `send*` / `refresh*` 等内部逻辑
8. **红点**：`update*RedDot`、触发红点的监听回调等

### View（`Win` / `Pop` / `UiComp`）

1. 字段：`v*`（默认不加注释）→ 其它业务成员（加注释）
2. `constructor`（有 `setWinMo` 则紧随其后）
3. **父类生命周期**：`initUi` → `onAddedToStage` → `onRemovedFromStage` → [`onClose`] → `initData`
4. **刷新**：`refresh*`
5. **自定义交互/业务**：`on*` / `play*` / `render*` 等
6. 其它私有辅助

## 方法内语句

没有特定顺序要求，但相关性较大的语句要尽量写在一起。

当方法中有较多语句的时候，可以按相关性分区，不同区之间用空行隔开。

# 编码规范

## 界面类

界面类一般继承自Win。

### 界面类的成员

- 子视图成员变量：变量名用v开头，可以自动接收fgui中的同名子元件
- constructor：调用super，设置界面所用的fgui资源、释放时机、所在图层。
- setWinMo：此时视图刚刚实例化，还没开始加载资源，用于对实例进行初始化，如果没有初始化的需求，可以不覆盖这个方法。
- initUi：此时视图资源已加载完毕，子视图成员变量也已经赋值完毕，可以对界面做一些初始化操作，包括按钮点击事件的监听。
- onAddedToStage：此时视图已经被添加到舞台上，可以监听外部数据变更事件。
- onRemovedFromStage：此时视图已经从舞台上移除，可以做一些清理工作，特例：在onAddedToStage使用listenMgr添加的事件监听已被自动移除，此处不用再调用移除。
- initData：此时界面initUi和onAddedToStage都已执行完毕，界面刚刚显示出来，可以刷新全部数据。
- refreshXxx
    - 每个视图，根据复杂度的不同，依赖的外部数据个数也不同。
    - 当外部数据很少，或者所有数据都是同时变化的，或者刷新视图的代价很小，那么就只需要一个笼统的refreshData方法，在里面刷新所有数据就可以。
    - 当外部数据很多，且不同数据的变化时机都不一样，有些变化很频繁，有些很少变化时，可以针对不同数据定义不同的刷新方法，以提高性能。

### 界面类方法的执行顺序

- 界面对象创建时，执行constructor
- 执行setWinMo
- 开始加载界面资源
- 界面资源加载完毕后，执行initUi
- 界面被调用show时
    - 如果界面还未添加到舞台
        - 将界面添加到舞台
        - 执行onAddedToStage
        - 执行initData
    - 如果界面已经添加到舞台（之前已经被show过而且还未关闭）
        - 执行initData
- 界面被调用hide时
    - 将界面从舞台移除
    - 执行onRemovedFromStage

### 界面类方法特别提醒

- 对一个界面对象来说，constructor、setWinMo和initUi方法只会执行一次，而其他方法会执行多次
- onAddedToStage和initData的区别是：每次show都会执行initData；但不是每次show都会执行onAddedToStage，当show之后还未关闭界面，再次show时就不会执行onAddedToStage。

### 职责边界（自己的事自己做）

封装：对象自己的状态与副作用由自己管理；父级只编排、只调公开接口。

- 子组件（Item/Com 等）：本对象上的缓动（`Tween.clearAll`）、特效清理、离台还原，在自身方法 / `onRemovedFromStage` 完成，不指望 Win 代清。
- Win/Pop：只编排流程（何时飞入、播特效、发协议），可调用子组件公开接口（如 `flyTo`/`resetFly`），不要直接 `Tween.clearAll(子节点)` 或替子组件维护 origin。
- Data：管协议与数据；真动画时长由 View 播完再回调发包，避免父级用固定 Timer 硬编码子组件动画。

反例：关界面后位置错乱——只改了坐标却未停缓动，或中断后完成回调仍执行。

## get/set方法

不写没用的get/set方法，比如 `get id():number {return this._id;} set id(value:number) {this._id = value;}`，这种情况下可以直接定义公有的id成员变量。

## Long类型

Long类型的变量仅用于协议域中，根据其变量含义的不同，在业务域中使用转换成不同类型的变量。

- 如果含义是id，则在业务域中使用string类型
    - Long转成string，用id?.toString()
    - string转回Long，用Long.fromString(id)
- 如果含义是可用于计算的数值，则在业务域中使用number类型
    - Long转成number，如果数值可能为0，用Long.toNumberOrZero(value)；如果数值不可能为0，才可以用value.toNumber()。用Long.toNumberOrZero比较保险，因为内部有判空，而协议中0值的Long是undefined
    - number转回Long，用Long.fromNumber(value)

## 数据变更事件（EventDispatcher）

`ModuleData`、功能对象 `*Fo`（如 `GrowSysFo`）继承 `EventDispatcher`（`src/script/core/event/EventDispatcher.ts`）。

### 派发

- 数据状态变更后调用 `this.eventChangeLater()`，统一派发 `EventType.change`
- 该方法延迟分发且可去重，避免一帧内重复刷新
- 参考：`GrowSysFo.onDataChange`、`ActShopData.reqSetCheck`

### 监听

- 其他模块 Data 或视图应监听**模块单例**的 `EventType.change`，例如：

```typescript
GrowData.I.on(EventType.change, this, this.updateAllShop);
this.listenMgr.on(ActShopData.I, EventType.change, this, this.refreshActContentData);
```

- 刷新 UI 时从 Mo 读取最新状态，不要依赖事件参数

### 养成等级相关

- 需要响应养成页等级变化（如商店 `buyLimit` 类型 6、`EnableConditionTypeId.GROW_PAGE_LV`）时，监听 `GrowData.I` + `EventType.change`
- **禁止** `for (const fo of GrowSysFo.instances) { fo.on(GrowSysEvent.upOk, ...) }`
    - `GrowSysEvent.upOk` 仅供养成界面 `GrowWin` 做升级成功表现
    - 该事件在 `updateMyData` 之前触发，且不覆盖登录、推送等数据同步路径

### 勾选/选中提醒

- 对齐活动商店：`ActShopData` 变更后 `eventChangeLater()`，视图 `ActTreasureTroveShopWin` 监听 `EventType.change`
- 不要为勾选状态新增带参自定义事件（如 `NOTIFY_SINGLE_CHANGE`）

## 红点性能

数据变更事件（`eventChangeLater`、`BagEvent.ALL_ITEM_UPDATE`、`GrowData` + `EventType.change`）触发频繁；红点逻辑须单独优化。

### 原则

1. **UI 与红点分离**：界面走 `EventType.change`；红点走 `RedDotTask.runLater()`（参考 `GodOriginData`、`ItemCraftData`）
2. **延迟去重**：使用 `RedDotTask` / `RedDotTaskList`，勿在高频回调里同步全量 `updateRedDot`
3. **避免重 getter**：`isBuyRedDot` 类 getter 含条件判断 + 背包查询时，勿在 `some/every` 热路径反复调用；优先 Mo 缓存 + 失效重算
4. **缩小范围**：聚合红点用可见集合（如 `shownGoods`）；单条变更只更新受影响商店/功能入口

### 反例

```typescript
// 背包每次变更 → 所有商店 → 全量商品 → 每条走完整 isBuyRedDot
private onAllItemUpdated(): void {
    this.shopDic.eachValue(shop => shop.updateRedDot());
}
```

`RedDotMo.setVisible` 仅在**最终值变化**时跳过分发，**无法避免前面的全量计算成本**。

## 杂项

- 不要将Po直接用作信息对象
- 非必要不要在any类型身上点属性或方法来用（不便于重构）
- 尽量不要用类继承，用组合的方式来实现。用继承后期不好管理，而且可能会引发js的类加载乱序问题，导致启动报错
